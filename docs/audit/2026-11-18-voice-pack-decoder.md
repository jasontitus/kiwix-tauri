# Voice-pack decompression and installation review

The app at `810e997` uses `bzip2 0.6.1` and `libbz2-rs-sys 0.2.6` to unpack the optional English Kokoro download. The updated installer uses `bzip2-turbo-rs` 0.1.0 with its `std` feature. On an arm64 Mac it used less time and more peak memory than the earlier decoder.

| Streaming decoder | Median elapsed | Median CPU | Median peak process RSS |
| --- | ---: | ---: | ---: |
| App baseline, bzip2 0.6.1 | 16.08 s | 14.58 s | 5.72 MiB |
| bzip2-turbo-rs 0.1.0 with its std feature | 10.77 s | 10.65 s | 10.12 MiB |

Each decoder streamed into the same buffered output. A separate process hashed the bytes. One warm-up per decoder preceded four measured fresh processes per decoder, alternating order. The host also ran builds and emulator work. The 181,886,349-byte compressed file matched the app's pinned SHA-256. All ten outputs were 221,801,472 bytes and had SHA-256 `ce23b8a10c500f7897abdcfbe1e35d711235fc6e8abb1228914dc71bb5fd192e`. The measurements cover decoding, output and resource use before installation or speech. [Individual samples](../benchmarks/2026-11-18-voice-pack-decode.json)

The replacement decoder has no runtime crates beyond the standard library. It forbids unsafe Rust. Independent tests covered single, empty and concatenated streams and returned an error for truncation, a bad block checksum and trailing garbage. The downloader authenticates the exact compressed bytes using SHA-256 and passes the same private file handle to extraction. The TAR reader uses the immutable release layout for names, lengths and types, rejects nonzero padding, checks the full expanded SHA-256 and reads the decoder through EOF. The separate Android factory input contains concatenated regular file payloads in the same order. The installer authenticates each payload and requires EOF. The static layout lists 38 directories including the root and 360 files totaling 221,488,168 bytes. [Pinned layout](../../src-tauri/src/kokoro/pack-v1.tsv)

### Admission, installation and recovery

A retained, access-checked application directory and an exclusive process lock serialize writers. The free-space preflight requires 240 MiB for the factory input and the additional 181,886,349 bytes for a download. The installer creates an isolated generation, publishes its complete journal header, and records each created member's filesystem identity. Publication verifies the expected tree and syncs it. An explicit repair keeps the previous selected generation available until the replacement is ready. Removal captures each identifiable member under a recoverable name and can resume after interruption. An older model without an installation record is detached and retained. A factory removal records the user's choice before deleting the selected copy. An explicit reinstall selects the new generation while retaining that fallback choice. If the new selection disappears or fails final validation, automatic installation remains suppressed.

A torn row, substituted file, interrupted header or unrecorded member can remain on disk. On a later authenticated installation the installer can verify the bytes of a partial member against the corresponding prefix in the new copy before reclaiming it. Settings offers repair for a missing model or a model-file verification failure. Successful repair reclaims a previous journaled generation only after authenticating the selected generation and validating the identities and contents of every remaining older file. If the new selection is damaged, a complete authenticated earlier selection is restored. Explicit removal detaches a damaged selection while retaining its payload. If final cleanup is interrupted, the next exclusive operation can resume it. An old generation with unprovable or changed entries is preserved. Repeated repairs after such changes can each leave up to the full 221,488,168 bytes of file payload plus filesystem overhead. A live failed extraction compares the current file with the bytes the app wrote before removing its staging generation. A cancelled or uncertain cleanup can wait until another verified installation. Permissions, disk failures, an unreadable record or a name occupied by an unrelated file can require freeing space or moving preserved data in the profile. The format makes no global bound on storage left across crashes.

Audio cache receipts bind a content key to a private file's identity, byte length and digest. The player uses the checked file handle. Eviction and removal preserve unreceipted files and changed replacements. A privacy or read-only cutover retires the playback and prefetch authority, cancels and drains installation and the background performance check, and prevents retired workers from publishing audio. Cached performance reports are tied to the measured model's filesystem identity.

### Native inference and verification scope

The three model inputs supplied to sherpa-onnx are checked against their expected contents. The app retains the checked descriptors and revalidates their identities before and after creating the engine. Sherpa opens ordinary filenames internally. A transient substitution by another process with the same account between those checks remains outside the guarantee. ONNX Runtime, the phoneme pipeline, the audio device, platform filesystem access controls and app WebViews remain in the application inventory. [Application inventory](../MEMORY-SAFETY-INVENTORY.md)

The host fixture tests exercise the genuine pack and the factory input with synthesized audio disabled. They cover reopen, interrupted extraction, replacement detection, removal, retained files and explicit factory reinstall. Unit tests inject a shortened journal write with a storage-full error and exercise both space preflight boundaries. They do not fill a user's volume. Earlier device speech and throughput observations in the runtime guide concern earlier releases. The table above measures decoding alone. [Runtime guide](../KOKORO.md)
