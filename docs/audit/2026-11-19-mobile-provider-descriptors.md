# Mobile provider descriptors

A document provider supplies an exact lease and the open parts for that lease. Rust borrows each descriptor only while it owns the lease, then duplicates it with close-on-exec through rustix. The duplicate becomes an owned `File`, and Rust checks that it is regular and seekable without changing the shared file offset. An incomplete batch drops the duplicates it already owns before scheduling release of the native lease. The archive reader retains the lease independently for the lifetime of its positioned readers.

The first review found that either native provider could overwrite an existing lease on an ID collision. Both now refuse that collision while preserving the old lease. The Android provider assembles its response before registering the lease, so an exception while building the response closes the unused descriptors without publishing a stale lease. The Rust adapter and reader keep a collision retry local to the same book, installation and provider reference. A matching successful reload retires the notice.

The repository source census counts **145 explicit production Rust `unsafe` blocks**, down from 147. The app accounts for 132 and the Windows MCP relay for 13. The separate declaration count remains 36. The provider adapter keeps one explicit `BorrowedFd` construction. Its safety depends on the native lease owning the returned descriptor through the synchronous duplication. Trusted Rust plugin calls reach the provider commands, and each native provider serializes publication and release of its leases. Both OS grant implementations and the Swift delegate hook remain in scope.

## Review and verification

Independent source review used base `eab3ff18ed76378df2034da74a84989c5b76152b` and six-path implementation manifest `58c0b66811754932e6c9f545f40c77068a491697766252a9bc68d060f04b0288`. It covered the native producers, descriptor lifetime, scope release on partial failure, the Rust file consumer, and reader retry authority. It also caught that the new error initially bypassed the reader's retry path. The final classification preserves the existing identity checks and explicitly admits the new temporary error.

- The ARM64 macOS app test executable `e143f289f6bcf9720adaf61ec355e3e2c050fad78bf4ee702ed633b68a48fb33` passed strict signature verification and 10 provider tests. The tests cover descriptor ownership and flags, offset preservation, rejection of non-files, continued use after the original is closed, and successful ZIM integrity checking and title search after modeled provider reconnection. Other cases cover revocation, part names and read-only restoration.
- Six frontend integration tests passed against the actual API boundary, error classification and reader error handlers. They cover collision retry for the exact installation and rejection of mismatched book, installation, provider and retry flag. TypeScript checking passed.
- Locked offline Rust app-library checks passed for ARM64 iOS device, iOS simulator and Android using `custom-protocol`. The Android provider's Kotlin module compiled offline against the installed Android SDK. Three Android provider unit tests passed for split-part names, missing descriptors and distinct acquisition failure codes.
- A signed standalone fixture `00aef19e53984d63a621576aa48d3f49f9a3352a2babfc18ebf02f35343403af` passed on a dedicated iPhone 15 Pro simulator running iOS 26.5. It compiled the production Swift document provider and the exact Rust duplication helper. A forced lease-ID collision preserved the first descriptor's device and inode. Rust's duplicate had close-on-exec set and left the file offset unchanged. After native release, the duplicate returned the four ZIM signature bytes. Reopening the source path verified all 128 original bytes. The XCTest source also passed a separate compiler check. The runner verified removal of the dedicated simulator.

The simulator used an app-owned temporary file and exercised the native provider class. Real file pickers, security-scoped or persisted URI grants, split-provider recovery on hardware and Android end-to-end behavior still need verification.
