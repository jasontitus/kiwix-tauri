# macOS system-share ownership

The Downloads command sends the installation ID displayed by the library row. macOS then retains the registered archive files, reads the archive ID from those descriptors and checks the stored file identity when an integrity receipt exists. Older registrations without a receipt establish authority over the currently admitted files at the registered path. The installation and archive IDs alone do not prove which bytes were present at import. The picker receives each retained split part in order. Legacy single-file ZIMs without a checksum field are admitted for reading. Split and destructive admission still require a declared checksum boundary.

The app captures the originating window and checks source, installation and policy before creating the AppKit share items and before opening the native menu. The menu uses the standard macOS Share item. Selecting it opens the system picker. The share reservation covers archive preparation, limits the app to one macOS system share and avoids holding the browsing-policy lock across filesystem work or UI. User-visible failures cover a busy share, a lost origin or policy, and files whose volumes cannot supply a stable reference. [AppKit's standard share menu item](https://developer.apple.com/documentation/appkit/nssharingservicepicker/standardsharemenuitem)

For each offered file, the app retains the descriptor and passes its device and inode numbers to the bridge. The bridge offers only a Foundation file-reference URL whose own file identity and volume match those numbers. This avoids offering the ordinary pathname and avoids a full file copy. The PDF path also rechecks the descriptor it validated before sharing. File-reference URLs have a volume lifetime and refer to the same inode through a rename. In-place changes by an outside writer can still change bytes. Compatibility on other volumes and with real share services remains open. [Foundation file-reference contract](https://developer.apple.com/documentation/foundation/nsurl/filereferenceurl())

The bridge closes its own menu or unselected picker when the wait is cancelled. Once a service is selected, Rust retains the request and source until the matching AppKit completion. The caller may stop waiting first and is told that a chosen service may still finish. A picker that never acknowledges closure or a selected service that never reports completion can retain the sole share reservation until restart and may leave PDF scratch behind. The checkout has 165 production Rust `unsafe` blocks across the app and relay, down from 166. The share callback no longer reads a native error string through a pointer. The native start and cancel calls remain.

## Verification

- The signed arm64 Mac fixture ran the exact bridge. It checked ordered file references, an original reference surviving a rename, and refusal of a replacement at the old name. Five requests exercised a hidden origin, authority loss after preparation, an inode mismatch, repeated cancellation and completion from the correct service. The service events were injected. The fixture never opened a share menu or performed a share. A separate local AppKit pasteboard test preserved the file reference through serialization and could not open the replacement after the original was unlinked. It used its own temporary files and pasteboard.
- The arm64 Mac application test binary passed 70 tests across native PDF, the shared request registry, library files and the PDF export service. Regressions cover PDF path replacement and read-only admission for legacy single-file headers. The frontend type check and bundle build passed. Vite warned that the host's Node.js 20.18.0 was below its stated minimum. Both arm64 iOS targets passed locked, offline app-library compile checks. The iOS checks cover compilation. Android and Linux runtime checks, visible share-menu interaction, actual service delivery and libzim comparisons remain open.
- Independent source and fixture reviews checked the affected frontend, Rust and native contracts. The corrections covered the installation ID, split-part order, policy locking, native menu API, authority checks, PDF file identity, bounded lifetime and the exact file-reference object rather than a separate leaf pathname lookup. The final production source manifest on base `3646e6f1d06afb171ec7af56ff135fe8a23f5199` had SHA-256 `bb3d5877c4a9a6b6917e97187e5f372ee3dba3f06335619da719376538d7b085` and recorded the registry move separately.
