# iOS background download command replies

Rust sends an immutable Foundation `NSData` command and a checked request ID. Swift snapshots the input before returning and owns the bytes through parsing on its serial queue. It lends immutable reply bytes to Rust for the callback. The old Rust heap pointer, raw C-string reads and C-string response lifetime are gone from this bridge.

The iOS bridge and Apple notification permission bridge use the same safe Rust registry implementation with separate request namespaces. Dropping a waiter removes its ID, and a repeated or unknown completion skips decoding. The registry releases its mutex before converting data or waking a waiter. A background command already submitted to Swift still runs when Rust drops its waiter. That distinction preserves the native privacy barrier and pending receipt work. Existing catalog provenance checks, durable download identities, policy admission, and Rust publication checks still control the operation. The native startup entry checks the main thread before attempting delegate registration.

The repository source census counts **147 explicit production Rust `unsafe` blocks**, down from 151. The app accounts for 134 and the Windows MCP relay for 13. The separate count of unsafe declarations is 36, down from 37. These counts exclude dependencies and test-only code. The Swift delegate still chains the prior method with `unsafeBitCast`. Its receipt filesystem code and app-owned adapters remain in the worklist.

## Independent review

The reviewed base was `28cc93821d57879d2dd999ab7a61464a99cc72c2`. Final source manifest `9750a85681aa7d9f6263244cbc9fd1899cdbc4cd4a8dbd0dc10a20d8438d181a` covers `BackgroundAcquisition.swift`, `apple_replies.rs`, `ios_background.rs`, `lib.rs` and `notifications.rs`. Review covered the selected C ABI and ownership on Apple ARM64, the Swift asynchronous command queue, dropped and duplicate replies, settings admission and receipt operations, and the existing notification authority checks.

The reviewer found an existing availability limit in native task retirement. If the operating system never calls back, a live waiter may remain pending because the deadline is checked inside the native callback. A dropped waiter now releases its Rust entry. Reliable recovery of commands that still have live callers remains open.

## Verification

- The ARM64 macOS app test executable `cd71ed6ef4a2c8d9c08dd0d4e48c2fe79576931af6d88acd97014d320f3425ec` passed strict signature verification and 12 tests. They exercised ID exhaustion, cancellation while waiting, duplicate replies, notification result and headless behavior, official-catalog provenance, and rejection of an invalid settings transition.
- The app library passed locked offline `custom-protocol` compile checks for ARM64 iOS device and simulator targets. Mac testing used Rust 1.99.1. The iOS checks used Rust 1.95.0. Both used Xcode 27 RC.
- A dedicated ARM64 iPhone 15 Pro simulator on iOS 26.5 ran the development-signed fixture `f8fbee739f387a2beb823e9541241961affa6d56e0e319806666a027106730ed`. It used the production Swift command handler and the exact Rust bridge and registry. The first process required fresh policy admission, applied a privacy restriction after the Rust waiter was dropped, ignored a replayed completion, and verified the rejection of a cleartext URL. It exercised receipt acknowledgment, idempotent stop and reconciliation using two seeded receipts. The second process required fresh policy, recovered the remaining receipt and acknowledged it. The two process IDs, successful Rust results and persisted file state agreed. Both receipts were removed and an unrelated file survived. The runner then verified removal of the dedicated simulator.

The first simulator attempt timed out during installation on iOS 27.0. On iOS 26.5, an ad hoc-signed build installed but yielded no result, and the Mac recorded a signature rejection. The first development-signed run failed without recording which assertion failed. The next run recorded the fixture error. It called the native entry directly and expected a host allowlist rejection. The native handler checks HTTPS URL shape, while the production Rust caller checks official-catalog provenance and may supply a resolved mirror. The diagnostic run confirmed one synthetic task submission for `example.invalid`. The final run uses a cleartext input that the native handler rejects before task creation. Cleanup verified removal of each earlier dedicated simulator.
