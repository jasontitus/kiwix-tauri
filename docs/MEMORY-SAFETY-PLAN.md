# Memory-safety plan

Make the application and its processing of untrusted data memory safe, including the dependencies reached through its safe APIs. The operating system and standard runtime are trusted. System WebViews and other OS-provided services sit inside that boundary. Application-owned native bridges, bundled engines, generated bindings and runtime libraries that process untrusted content remain in scope. Keep the MIT Zimru reader and writer and the GPL Xapian reader and builder in their separate source and license histories. Commit and push this work to the private repository.

At `b20d19c`, the production Rust census has **166 explicit `unsafe` blocks**, 153 in the app and 13 in the Windows MCP relay, plus 41 separate unsafe declarations. PDF and sharing account for 39, Apple Nearby for 25, and connector authentication and private-sync identity for 41. The other 61 are spread across platform code. The scan covers `src-tauri/src` and `kiwix-mcp/src` and excludes test-only code and dependencies. Track the shipping dependency and native-code inventory alongside this count. ## Implementation order

Start the dependency work while the platform changes are under review. Batch changes with the same producer and consumer contracts so an independent review and platform build can cover the full change. Repeat the focused checks after fixes, and run the full platform matrix at integration checkpoints. Expect days for substantial first-party reductions and multiple weeks for whole-app verification with the existing feature set. Re-estimate after the TLS and speech experiments establish what can ship.

## Performance and platform verification

- Build and test the packaged release configuration on macOS, iOS, Android and Linux, using the designated Linux host when needed. Exercise the changed runtime path on each affected platform. Record simulator and emulator results as such, and follow the repository's physical device testing windows. Include supported 32-bit Android coverage where limits or offsets differ. Keep fixtures and exact build receipts and clean up owned temporary builds. [Packaging and device checks](PACKAGING.md) · [Independent review and device workflow](../AGENTS.md)
- Compare complete operations against libzim on the same archive, hardware and build settings. Capture warm and cold article open, random reads, media ranges, search, verified import and applicable build throughput. Check result bytes and ordering and record elapsed time, CPU and peak memory. Aim for comparable or better performance. Favor the safe implementation when a complete operation already takes under 50 ms and the added latency is acceptable. [Existing measurements and performance switches](MEMORY-SAFETY-INVENTORY.md#performance-follow-up)
- Keep performance-switch enablement on the worklist until the release app results justify a default by platform. Compare current and candidate settings with the native reference under the same cache budget, including physical Android and iOS before changing mobile defaults. Record exceptions by operation and platform.

## Completion evidence

- Identify the release revision, features, libraries and owners of the paths that accept archive, network, model or provider input. Inspect compiled Rust and native code and their reachable consumers. Replace unsafe processing outside the trusted platform. For each residual call into the trusted platform, record its native owner, inputs, lifetime and cancellation obligations. Enforce safe application code wherever the boundary has been removed and keep remaining gaps visible until they are closed.
- Obtain independent adversarial review of every change batch, including docs and all new files. Record tested failures, finding dispositions, exact source and artifact identities, and unresolved runtime or hardware gaps. Re-review affected paths after fixes. Progress updates report both changes in the source census and which untrusted-input paths are verified.
