# Safe Rust decoder performance on four platforms

Kiwix Tauri's build revision `6d8a058dada452cc171c80c386cf996742485868` uses MIT Zimru `ff8b0ab5e561b0019151d6d614131f59920ff2ee`. Zstandard sequence execution loads checked 8- or 16-byte arrays by value before storing them. Later copies can read bytes produced by an earlier copy in the same match. The decoder keeps its exact-length path near the allocation limit and verifies frame history, block sizes, output bounds and checksums. The separate GPL search engine remains at `380d84d7bb4ba9f30144462fd6bb18e932493fc0`. [MIT implementation and regression test](https://github.com/jasontitus/zimru-xapian/commit/ff8b0ab5e561b0019151d6d614131f59920ff2ee)

## Application cache and verified import

Kiwix configures a 32 MiB decoded cluster cache for each archive. A separate Mac comparison gave both libraries that budget and used the same requests and output hashes. The 24 random Climate reads took 18.32 ms with libzim, 28.62 ms with previous Rust and 22.08 ms with optimized Rust. On Wikipedia 100 they took 32.40, 40.66 and 33.86 ms. Rust's media ranges took 2.59 ms on Climate and 0.120 ms on Wikipedia 100, against 2.91 and 0.235 ms with libzim. [Mac production-cache samples](2026-11-18-macos-production-cache.json)

Linux used the same compiled prototype as its 4 MiB comparison. With a 32 MiB cache, random reads took 25.42 ms native and 36.03 ms optimized on Climate, and 48.83 ms and 57.02 ms on Wikipedia 100. Whole-process CPU for Wikipedia 100 was 57.37 and 60.24 ms. Its media ranges took 0.272 and 0.177 ms. At 4 MiB, optimized Rust also reduced whole-process random-read CPU relative to previous Rust on both archives. ## Verification and open differences

The reader-only, default and all-feature MIT suites passed 117, 188 and 197 tests respectively, including doctests. The vendored codec passed 53. The reader's three real-archive tests were also repeated with mandatory fixtures. On six complete Wikipedia archives, the Rust decoder and a reference build using the native codecs produced the same 314,625,161 bytes of length-framed blob data. The promoted codec also reproduced all 128,005,261 native-decoded bytes from the original 65 Zstandard frames. An independent comparison against one-byte-at-a-time match expansion covered 851,466 overlap, length and spare-space combinations. Other experimental changes to bit refills and output bounds remain outside this app build.

The release GPL search and suggestions CLI matched all 120 recorded ordered top-ten lists on Climate and Nollywood. Both native CJK comparisons were repeated using the optimized reader and the existing GPL builder. The complete result files matched those from the previous checkpoint. Xapian 1.4 matched 63/63 ordinary Chinese, Japanese and Korean queries. Xapian 2.0 matched 61/63, with differences for the fullwidth “ＡＩ” and “１２３” queries. Both matched 6/12 rare-Han queries. The index comparison and ordered search results are recorded separately in the search project's audit. [GPL search comparison and method](https://github.com/jasontitus/zimru-xapian/blob/380d84d7bb4ba9f30144462fd6bb18e932493fc0/AUDIT.md#cjk-archive-comparison)

The writer experiment remains separate. The reviewed whole-archive study contains 108 native, current Rust and experimental Rust samples on three archives at levels 3 and 19, with one and four workers. At level 19 the experimental writer beat native throughput on five of six archive/worker combinations. Nollywood with one worker took longer. An earlier Linux single-worker level-3 fixture produced output near twice native size. The later 6 and 12 MiB repeat comparisons used different inputs or native frame sizes. Reproducing the original size gap remains open. These findings concern archive creation; the app uses the reader-only feature set.
